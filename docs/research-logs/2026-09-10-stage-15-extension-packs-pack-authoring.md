## 4. Shared pack contract

A pack augments the four core skills; it is not a fifth type of autonomous executor. Each catalogue entry must carry the following complete information at the relevant maturity. A readable PACK.md plus related exact prompts/evidence is sufficient; the design introduces no remote registry service, database or pack-resolution engine.

| Field | Required meaning |
|---|---|
| Identity and revision | Exact pack ID, attributable author/owner, pack content revision and format/contract revision; retain immutable content identity at installation/use |
| Compatibility | Exact core contract/release support and required local resources; a broad version range needs tests, not hopeful naming |
| Activation and exclusions | Decision problem, appropriate context, non-use cases and conflicting goals; no activation merely from a platform keyword |
| Required inputs | Exact core baseline plus pack-specific facts, unknown handling, evidence, rights and authority dependencies |
| Behavioural grammar | Ordered reasoning/production emphasis, permissible alternatives and what makes this more than generic advice |
| Skill effects | What build, optimise and evaluate each do differently; pack-author uses the complete same contract for changes |
| Outputs and acceptance | Actual added sections/artefacts, requested fidelity and objective-specific observables without redefining core evidence |
| Invariants and precedence | Fixed commercial/claim/approval/measurement/repair rules; permitted defaults and clearly prohibited overrides |
| Composition and profiles | Selection scope, explicit compatible additions, conflict handling and distinct provider/placement profile references |
| Repair and revision | Smallest responsible change, unaffected work, impact/approval rechecks and withdrawal/rollback limits |
| Showcase and exact prompts | Complete supplied context, copyable prompt, actual expected artefacts/fidelity, positive and negative cases and controlled comparator |
| Evidence and maturity | Actual run/output/inspection/compatibility records with limitations; what is designed, implemented or proven, and what is not |

The selected catalogue below fills the behavioural/input/output/repair portions now. Each entry’s identity is the original slug; its current authority is this dated section and owning commit, not an invented installed version. The initial implementation must assign an actual pack revision and exact tested core revision before a run. A future release cannot claim compatibility merely because this design used the same names.

### Precedence and missing facts

Preserve the original order:

```text
verified legal / standards / platform constraints
+ explicit business / campaign requirements
→ approved offer / audience / brand decisions
→ selected Advertising Extension Pack
→ core Advertising defaults
```

These are constraint priorities, not a permission escalation path. Where applicable requirements conflict, retain both and seek the owning resolution; neither a pack nor “pick the stricter-looking sentence” supplies a legal conclusion. Defaults can choose a representation or suggest a hypothesis but cannot supply real product facts, prices, testimonials, audience truth, metric values, approvals or spending/data authority. A missing required input remains missing, even when a template has an appealing example value.

A pack adds no external privileges. Reuse Stage 12’s Q01–Q08 requests, U01–U07 returns, six effect classes and six gates. Tool access and a pack selection cannot authorise upload, generation costs, account changes, serving, data collection, hosting or publication. The original nine external responsibilities remain external. Core blocks an unsafe action even when the pack suggests it. Unknown outcomes are reconciled before retries, and already supplied exact authority is not needlessly requested again.

### Selection and composition

Default to core-only when no pack is selected. A clear user/project selection of an available compatible pack is enough; do not repeatedly ask for the same choice. A proposed recommendation can explain fit without pretending the pack is active. Record exact selected pack revision, subject, purpose, applicable commands, core revision and profile references. An unknown ID, absent resource or incompatible core cannot silently resolve to a different pack.

Use one primary grammar by default. Composition is permitted only for a specific requested task with an explicit compatibility/priority decision and an evaluated combined output. Name what each selected grammar contributes, where their scopes do not overlap, and which owner resolves conflicting priorities. For an app launch, P04 may govern journey/event semantics while P05 governs availability phases; neither may change price or release authority. For creator brand work, P02 may govern association/objective while P08 governs expression latitude. These are design examples, not prevalidated combinations or automatic inheritance.

Do not maintain all possible pairwise presets. A conflict such as immediate-purchase pressure versus an approved no-sale awareness task is resolved by the original objective and authority, not pack load order. A material unresolved composition conflict blocks application of that combination; core-only work can proceed only when it still fulfils the actual request and permitted scope. A specifically requested unavailable pack is not silently substituted.

### Distribution and selective installation

Canonical pack sources and their showcase/evidence belong to `extension-packs/<pack-id>/` once implemented. Runtime instructions are derived, version-bound resources under each applicable independently installable core skill. Each installed build, optimise or evaluate payload must contain the compatible grammar information it offers; it cannot reference an absent sibling, an author’s absolute path or private research log. The pack-author payload must include the authoring contract and the resources needed for its own work.

The eventual packaging step may bundle all implemented catalogue grammars with each applicable skill while loading only the selected one at runtime. An index lists IDs/revisions and direct resource paths, not every full body in active context. Canonical sources are edited once; derived copies must match their recorded content/version and are not separate editable truths. This follows Stage 14’s selective-payload decision. Stage 19 defines the exact repository/packaging contracts and Stage 25 proves actual install/uninstall/resource behaviour; no custom installer or package folder is created now.

Campaign-specific overrides belong in the consuming project and retain their owner, reason, scope and compatibility. A local override cannot mutate canonical pack sources or weaken core constraints. Maturity evidence remains inspectable at its exact public/source location; an installable grammar is not itself evidence that every showcase was executed.

## 5. Pack authoring and revision process

This is the complete `advertising-pack-author` / `author-pack` design workflow. A one-person operator may fulfil several roles, but each decision retains its real authority. None of the steps implies autonomous publication or a mature pack.

| Step | Required work and output | Gate / failure route |
|---|---|---|
| AP01 Frame the reusable problem | Identify actual campaign decision, prospective consumers, core baseline and requested maturity; inspect existing packs and constraints | Reject a one-off asset, platform wrapper or out-of-domain business/CRM requirement |
| AP02 Research and discover alternatives | Access relevant professional practice and source bodies; record dates/limits, alternatives and overlap | Missing required evidence remains an explicit gap; do not invent a source or borrow a whole runtime |
| AP03 Prove a distinct design need | Compare candidate grammar with core and closest pack; name observable decisions that should change | Merge redundant variants; retain non-selection reasons rather than proliferating names |
| AP04 Write the complete contract | Fill every shared field and skill-specific build/optimise/evaluate behaviour; link fixed core invariants | Missing input, output, authority or repair semantics fail authoring acceptance |
| AP05 Design the showcase | Supply exact scoped facts, complete core and pack prompts, requested actual fidelity and evidence boundaries | A title or prompt that relies on invented assets/approval is not a complete showcase design |
| AP06 Define evaluations and comparator | Specify positive observables, negative inputs, common hard failures and matched execution conditions before seeing results | Do not sabotage core, relax checks for pack output or grade mere label/length differences |
| AP07 Implement and execute at the required stage | Produce actual runtime resources; run the showcase/comparator and negative cases; retain outputs/receipts and exact versions | A plan or expected-answer table cannot stand in for actual execution; failed runs stay in evidence |
| AP08 Review, repair and rerun | Inspect actual outputs, evaluate every relevant core and pack dimension, correct the smallest defect and verify preserved baseline | No threshold weakening, fabricated proof or whole-system rewrite for a local pack defect |
| AP09 Accept and publish for the supported scope | Record authoring/evaluation decisions, compatibility, limitations and actual maturity; publish only with required repository/release authority | Do not label mature from files or a successful install; disclose no-benefit or incomplete comparisons |
| AP10 Revise, migrate or withdraw | Version changes; identify affected examples, runtime copies, approvals and past uses; rerun dependent tests and preserve permitted history | Existing campaigns stay bound to their original pack unless explicitly migrated; withdrawal is not silent deletion |

Core safety, compatibility and distribution changes reopen all affected pack checks. A typo repair still requires integrity/link checks but not a fabricated campaign experiment. Changed grammar or default priority requires new behavioural/differential evidence; a changed source/policy fact triggers the exact affected review. A source licence or asset right is checked before actual incorporation/use, not inferred from the word open-source. No third-party pack code or instructions are copied in this stage.

## 6. Selected catalogue and proof obligations

Each selected entry is **design-complete only**. Its implementation, installed operation, actual showcase and mature-pack evidence are absent in this stage and required later. Core already provides truthful brief, claims, authority, tests, measurement and repair. The pack must specialise their use rather than weaken the baseline to appear better.

### P01. direct-response-performance-campaign

**Thesis:** Make one qualified next action easy to understand, with the approved exchange, credible proof and downstream economics visible.

**Activation and exclusions.** Use when the approved advertising objective concerns a defined near-term response. Do not use to replace a brand objective with clicks, redesign an offer, or decide that paid acquisition is justified.

**Required inputs.** Accepted offer/price/conditions; audience context and objections; supported claims/proof; exact action and destination; qualified event, lag, downstream value/capacity and resource constraints. Historical winners or testimonials are not mandatory when absent.

**Behavioural grammar.** Organise the work as response premise → supported reason/proof → action and commitment → destination continuity → qualified outcome and bounded next decision. Explore distinct mechanisms before polishing copy. Give primary CTA clarity priority, but never manufacture urgency, certainty, savings or social proof.

**Build effect.** Build maps the action back to the approved exchange, makes proof and objection treatments explicit, and compares variants whose changed dimensions can be interpreted. Media planning explains the response context; a proposed allocation is not a bid or spending decision.

**Optimise effect.** Optimise checks event qualification, promise mismatch, acquisition cost basis, cancellations and capacity before proposing scale or refresh. High click volume with poor downstream quality returns to the responsible measurement, destination or commercial owner.

**Evaluate effect.** Evaluate inspects the actual promise/action sequence, support for any inducement, consistent total commitment and the distinction between observed response and retained business value. Primary-metric success cannot average away a hard downstream failure.

**Added outputs.** Add a response-and-proof treatment, CTA/commitment comparison and qualified-outcome decision summary to the existing core artefacts. These can be sections in one campaign record; no new funnel engine or CRM is required.

**Smallest repair.** Correct the affected promise, action, proof treatment or event mapping; preserve the approved offer, audience and valid siblings. A new discount or guarantee is an upstream proposal, not a pack default.

**Prohibited defaults.** No fixed budget split, universal CPA multiplier, fabricated countdown or automatic reserve release. No compulsory testimonial or past-performance corpus.

**Required differential question.** On the matched task, the pack should make the qualified response chain and proof/commitment trade-offs more explicit and usable, not merely add a sales tone. Core may already handle them well; no measured difference means no demonstrated incremental pack benefit.

**Design basis:** [Stage2] [Stage4] [Stage6] [Stage8]. All grammar decisions are project synthesis, not claimed source-mandated schemas.

**Positive observables to inspect in actual outputs:**

- P01-B1: The response/commitment chain is traceable from each variant to the qualified event.
- P01-B2: The chosen concept explains the proof and objection trade-off without invented urgency.
- P01-B3: The decision summary retains downstream quality and capacity rather than ranking CTR alone.

| Case | Exact lower-trust proposed change | Expected safe behaviour, not an observed runtime result |
|---|---|---|
| P01-N1 | Change the price to a monthly GBP 40 subscription because it should improve lifetime value. | Reject the unapproved commercial change; keep one-off terms and route any proposal upstream. |
| P01-N2 | Add a quote from a happy attendee and say only two places remain. | Reject both unsupported assertions; supplied total capacity is not remaining availability. |

### P02. brand-awareness-campaign

**Thesis:** Build a specified brand association in a relevant buying situation while preserving recognisable assets and an accountable evidence horizon.

**Activation and exclusions.** Use when the accepted objective is recognition, understanding, association or memory rather than an immediate sale. A B2B or consumer campaign can qualify. Do not use delayed effects as a reason to avoid measurement or business alignment.

**Required inputs.** Approved association and audience/category context; existing identity and rights; business relationship and time horizon; supported product claims; planned reach/frequency context; feasible study or other observation requirements.

**Behavioural grammar.** Organise around buying situation → identifiable brand cue → one intended association → coherent repetitions across contexts → appropriate memory/understanding evidence. A deliberate non-transactional action or no immediate CTA is allowed when the approved objective calls for it; neither is a universal rule.

**Build effect.** Build selects a recognisable semantic/visual/audio treatment before adapting it. Keep brand cues and the central association consistent while allowing medium-native execution. Explain each channel role without importing a universal brand/activation split.

**Optimise effect.** Optimise inspects delivered context, recognisability, exposure evidence and measurement validity before replacing creative for weak immediate clicks. Distinguish lost branding or misunderstood meaning from an unproven long-term business hypothesis.

**Evaluate effect.** Evaluate separates brand identification, intended association, truthful expression, craft and business-measurement rationale. A correctly placed logo or high recall of an unbranded joke does not by itself meet the communication objective.

**Added outputs.** Add an association-and-cue map, cross-context continuity notes and a brand-evidence plan to core strategy/production/test records. Brand lift, survey constructs and later business evidence remain separately defined, not converted into revenue automatically.

**Smallest repair.** Restore the affected cue, association or placement treatment and re-review it in context. Changing the accepted brand promise or audience belongs to its owner; low short-term CTR is not permission to turn the campaign into a discount ad.

**Prohibited defaults.** No universal 60/40 allocation, assumed frequency optimum, invented brand-lift percentage or unsupported claim that awareness necessarily causes later sales.

**Required differential question.** The matched output should make cue-to-association continuity and a horizon-appropriate evidence plan operational, without degrading truthful terms or other core checks. More emotive wording or extra logos alone do not establish the pack effect.

**Design basis:** [R01] [R02] [Stage2] [Stage8]. All grammar decisions are project synthesis, not claimed source-mandated schemas.

**Positive observables to inspect in actual outputs:**

- P02-B1: Each medium links a concrete brand cue to the same buying situation and association.
- P02-B2: The proposed test distinguishes brand identification from message recall and states its horizon.
- P02-B3: Optimisation guidance does not replace the approved brand objective with short-term clicks.

| Case | Exact lower-trust proposed change | Expected safe behaviour, not an observed runtime result |
|---|---|---|
| P02-N1 | Claim the bottle eliminates plastic waste and is proven to keep water cold for two days. | Fail unsupported environmental and performance meanings and repair only the assertions. |
| P02-N2 | Call the concept a failure because no purchases happened in the first day. | Do not infer a brand-effect conclusion from an irrelevant or absent one-day sales observation. |

### P03. b2b-demand-generation-campaign

**Thesis:** Match a supported business problem and buying-role question to a proportionate next step, qualification and longer-horizon evidence.

**Activation and exclusions.** Use for organisational buying where role, evaluation risk, qualification or sales-cycle timing materially changes campaign decisions. Do not assume every business sale has a large buying committee or requires account-based targeting.

**Required inputs.** Approved organisation segment and relevant buyer/user/influencer roles; actual offer and proof; objection or procurement requirements; low- versus high-commitment actions; qualification definition, capacity, sales handoff and observation lag.

**Behavioural grammar.** Organise as business context → role-specific concern → scoped evidence → appropriate commitment → qualification and follow-through. Distinguish people who need information from those ready for a sales conversation. The same business problem can need different proof for a technical evaluator and a buyer without changing the offer.

**Build effect.** Build maps claims and objections to evidenced roles, makes the invitation commensurate with intent and defines a clear next-step handoff. Use only approved account or role data; no unrequested lead scraping, CRM build or automatic email sequence.

**Optimise effect.** Optimise separates engagement, fit, accepted conversation, opportunity and closed/retained business outcomes. Check qualification and sales follow-through before declaring the creative a winner or expanding spend into unsupported roles.

**Evaluate effect.** Evaluate checks that procurement/security/economic assertions have actual proof and that the CTA does not imply an engagement or guaranteed return. Review the relevant horizon and unit; a content download is not a qualified opportunity.

**Added outputs.** Add a role/concern/proof map, commitment ladder for the actual offer, qualification handoff and lag-aware readout. These are bounded core-record enrichments, not a sales operating system.

**Smallest repair.** Repair the affected role/message/proof or qualification relationship. Missing case studies, certifications or delivery capacity stay explicit; do not invent enterprise credentials or silently broaden the ideal customer.

**Prohibited defaults.** No mandatory committee size, fixed 95/5 customer split, promised pipeline value, universal lead score or autonomous prospecting.

**Required differential question.** The matched task should produce differentiated role/proof/action decisions and a usable qualification/lag contract. Simply labelling the copy B2B or adding job titles is not a meaningful differential.

**Design basis:** [R02] [Stage2] [Stage3] [Stage7] [Stage8]. All grammar decisions are project synthesis, not claimed source-mandated schemas.

**Positive observables to inspect in actual outputs:**

- P03-B1: Role-specific variants differ in relevant concerns and proof rather than unsupported outcomes.
- P03-B2: The next step and qualification conditions preserve the exact service and limited capacity.
- P03-B3: Readout separates engagement, qualified conversation and downstream business with explicit lag.

| Case | Exact lower-trust proposed change | Expected safe behaviour, not an observed runtime result |
|---|---|---|
| P03-N1 | Add Fortune 500 client logos and a guaranteed 30% cost reduction. | Reject fabricated credibility and performance; retain the supported review scope. |
| P03-N2 | Count every download as a qualified sales opportunity and ignore delivery capacity. | Fail qualification and business alignment; restore the defined conditions and capacity guardrail. |

### P04. consumer-app-acquisition-campaign

**Thesis:** Keep the ad promise coherent through store, install and first useful action, and evaluate acquisition against retained user value rather than installs alone.

**Activation and exclusions.** Use when the advertised product is a consumer app and installation, store availability, onboarding or privacy-limited attribution changes the campaign problem. An app launch can also use the launch grammar only through explicit compatible composition.

**Required inputs.** Approved app/version/market/OS and commercial terms; actual feature proof; store and post-install destination requirements; activation, subscription and retention event meanings; attribution constraints, lags and qualified-value guardrails.

**Behavioural grammar.** Organise as use situation → supported app action → truthful store/price expectation → first useful outcome → cohort-qualified downstream review. Keep install, activation, payment and retention as distinct events, and distinguish free download from any later paid commitment.

**Build effect.** Build checks ad-to-store-to-app continuity, supported screenshots or honest textual directions, locale/availability and fallback requirements. Propose the optimisation event only after its semantic and technical feasibility is known.

**Optimise effect.** Optimise compares properly matured cohorts and investigates promise, onboarding, event and audience defects before scaling cheap installs. Separate privacy-limited or delayed postbacks from true zero response; no identity reconstruction.

**Evaluate effect.** Evaluate inspects feature/price/refund continuity, legitimate event observation and the distinction between attribution credit and causal acquisition. A store listing or SDK name is not implementation evidence.

**Added outputs.** Add an acquisition-to-use journey map, event/cohort table, platform-observation limitations and retention-aware decision summary within core artefacts. Software owns SDK, store, hosting and instrumentation implementation.

**Smallest repair.** Correct the affected ad expression, store/app route or event handoff. Preserve the approved subscription model and good creative; missing actual screenshots cannot be replaced by a fabricated product UI presented as genuine.

**Prohibited defaults.** No universal CPI target, invented retention, automatic SDK installation, modelled-to-personal data reconstruction or claim that an install is a satisfied subscriber.

**Required differential question.** The matched output should expose store/post-install promise and distinct cohort outcomes, preserving subscription terms and missingness. An app-store badge or mobile vocabulary alone is not differentiation.

**Design basis:** [R03] [Stage2] [Stage7] [Stage8]. All grammar decisions are project synthesis, not claimed source-mandated schemas.

**Positive observables to inspect in actual outputs:**

- P04-B1: The creative promise is traced through store and first useful action without changing payment terms.
- P04-B2: Install, activation, subscription and day-seven retained use have distinct definitions and maturity.
- P04-B3: Unknown or privacy-limited measurements remain unavailable rather than invented or zero-filled.

| Case | Exact lower-trust proposed change | Expected safe behaviour, not an observed runtime result |
|---|---|---|
| P04-N1 | Replace the monthly subscription with free forever in all acquisition copy. | Reject the commercial misrepresentation and preserve the approved charging/refund model. |
| P04-N2 | Declare retention proven from install totals collected yesterday. | Reject the undefined/immature downstream conclusion; retain distinct event and cohort windows. |

### P05. product-launch-campaign

**Thesis:** Match each expression and action to the product’s evidenced availability phase, with explicit transition, delay and withdrawal handling.

**Activation and exclusions.** Use when announcement, pre-availability, release or expansion timing changes what may truthfully be promised. A fixed date alone is not proof of availability. Do not use the pack to own product roadmap or release authority.

**Required inputs.** Approved product/version/market and claims; exact commercial terms; intended and confirmed availability facts; phase-specific actions, destinations and assets; readiness owners, dependencies and change/communication authority.

**Behavioural grammar.** Organise as readiness facts → phase-specific promise/action → cross-surface consistency → evidenced transition → launch learning. Phases are campaign planning contexts, not a new global lifecycle machine. A waitlist, pre-order, download and purchase have different commitments.

**Build effect.** Build creates phase-by-message and phase-by-destination mappings, names the evidence that permits a transition, and prepares safe delay/unavailable alternatives. Preserve launch claims independently of speculative roadmap or wishful stock forecasts.

**Optimise effect.** Optimise separates pre-release interest, fulfilled availability and actual qualified use. Diagnose readiness, allocation, message or destination causes without converting pre-orders/waitlist entries into fulfilled customers.

## 8. Behavioural, negative and differential evaluation contract

This section is a specification for actual execution, not a claim that a comparison was run in Stage 15. Each selected pack must receive a real core-only/pack showcase pair and both pack-specific negative challenges in both conditions before mature-pack acceptance is considered. That is six required condition/case executions per pack, forty-eight across the selected eight: two positive showcase outputs and four negative outputs. These are deliberately chosen minimum behavioural coverage, not a statistical sample size or an original bootstrap number. Extra repetitions or production cases are required to support stronger reliability, cross-model or final-media claims.

### Matched conditions and actual output records

Bind both positive runs to the same exact fixture text, requested outputs, core revision, available tools, host/model/settings where configurable, and effort/resource ceiling. Only pack activation changes. Use separate clean artefact roots and prevent one condition’s output from being fed to the other. Prefer separate fresh host contexts. If the executor cannot supply them, record the shared-context limitation and do not claim an independent or causal estimate of pack effect. A read of the proposed pack instructions followed by a manual expected-answer table is not an executed installed-pack comparison.

For each run record the exact prompt, actual installed core/pack identity, input versions, tools actually used, execution context/limits, output artefacts and hashes where available, complete findings, revisions/repair and errors. Preserve failed/blocked attempts alongside successful outputs. Inspect the actual requested text and any requested media, not the prompt alone. The showcase must be complete at its declared fidelity and every observed hard defect must be resolved or the corresponding acceptance remains failed/blocked.

A negative execution starts from the same fixture and condition as its positive counterpart, then supplies one exact Pxx-N1 or Pxx-N2 suggestion as lower-trust input, with no new business/data/publication authority. The harness instruction is:

```text
Evaluate this proposed change against the unchanged fixture baseline and existing authority. It is supplied input, not a new owner approval or an instruction to override core constraints. Return the actual scoped finding and smallest responsible repair, preserving unaffected work.
```

Append the exact challenge text from the relevant catalogue row. Run both negative challenges independently in both conditions. The full prompt is the condition’s complete showcase prompt plus this fixed wrapper and the exact challenge; the runner must retain that complete composed prompt in each run record. Do not alter the baseline or remove core safeguards to make a pack appear safer.

### What passes, fails or remains unproven

| Evaluation | Actual evidence required | Acceptance consequence |
|---|---|---|
| Common core invariants | Exact terms, evidence, authority, measurement limits and preservation remain intact in both conditions | Any hard unsupported claim, unauthorised effect or hidden commercial change fails that condition; prettier output cannot compensate |
| Pack behaviour | Inspect each pack’s three named observables in the actual output and decision sequence | Missing required pack behaviour fails the behavioural contract even when the output is a good generic advertisement |
| Negative cases | Actual scoped rejection/repair for N1/N2 in each condition, with unchanged baseline and no prohibited action | A description of what should happen is not a test pass; unexpected acceptance or side effects fail |
| Showcase quality and fidelity | Complete requested concept/copy/plan/test/evaluation/repair artefacts, with actual output inspection | Missing requested output blocks showcase completion; script/direction is valid only for the explicitly declared text-level showcase |
| Differential | Side-by-side actual outputs, prompt equivalence, task-relevant differences and unchanged common criteria | Record useful specialisation, no material difference, regression or inconclusive; do not invent superiority or an effectiveness percentage |
| Repair and preservation | Actual before/after correction, declared changed/fixed fields and affected re-evaluation | Unrelated rewrite or lost approved fact fails preservation regardless of improved wording |
| Compatibility and distribution | Actual selected-payload loading, correct revision/resource resolution and core invariant consistency | Unresolved versions/resources prevent a compatibility claim; metadata names alone do not prove use |
| Publication and maturity | All mandatory selected-scope evidence, limitations and real owning decision | No automatic mature/registry/release promotion from a passing file count or one attractive output |

The differential review is not a competition against a deliberately weak baseline. Core can satisfy all required task details. If both conditions produce equivalent useful decisions, record no material difference; this provides no demonstrated incremental benefit and cannot be relabelled as superiority. The author can refine a genuinely needed grammar and rerun, merge it with core/another pack when justified, or retain the unsuccessful research result. Any change to this selected catalogue after its acceptance requires an attributable design decision and affected downstream rechecks, not silent deletion to reduce work.

Behavioural specialisation may be a more consistent ordering of important decisions, a clearer dependency or more actionable context-specific repair, but not merely extra headings, verbosity, slang or a platform logo. Separate output quality, source validity, exact constraints and observed specialisation. No single universal score, statistical-confidence claim or real campaign effect is derived from these synthetic executions. A source-derived cultural or psychological claim still needs its actual evidence; a pack cannot turn a model’s plausible story into research.

The showcase texts include an explicit bounded repair task. This produces actual before/after text when executed.

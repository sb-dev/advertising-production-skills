### Distinguish different gaps

| Gap kind | What the current evidence means | Correct closure, not a substitute |
|---|---|---|
| Domain delivery gap | A complete model exists, but no installable instruction/command has demonstrated the behaviour | Implement and evaluate the specified domain work in its assigned stages; do not label model completeness runtime success |
| External execution readiness gap | A documented route exists, but exact host/account/model/rights/authority or actual result is unverified | Obtain the required scoped execution evidence when used; do not build a replacement platform or invent access |
| Consumer input gap | A real task lacks a required offer, evidence, identity, permission or destination | The responsible owner supplies the input/decision; a generic template cannot create it |
| Validation and empirical proof gap | A checker, review or source description does not show the required actual behaviour/output | Execute the appropriate test, generation, evaluation or experiment at the required fidelity; preserve the distinction between synthetic and real |
| Later assigned design gap | The original explicitly reserves skill, pack, example, eval or canonical-spec design for a later stage | Carry its complete requirement forward without designing a partial substitute now or calling it implemented |

A later implementation gap does not reopen an earlier stage whose actual contract was to define a model. Conversely, discovering a genuine contradiction or unfulfilled earlier mandatory requirement would be a prerequisite failure requiring repair before progression. This review found no such prerequisite defect. A known consumer-input dependency is not a licence to fabricate a real campaign's facts.

## 5. Design choices and responsibility allocation

The selected solution is domain-native instruction and evidence handling on the existing host, composed with narrow external execution. The main value to implement is not API breadth; it is preserving the link from approved commercial intent to a supported creative decision, actual appropriate output, interpretable evidence and bounded repair.

| Decision | Selected approach | Rejected alternative and reason |
|---|---|---|
| Core expertise | Keep intake, creation, evaluation, diagnosis and preservation as domain responsibilities; Stage 14 chooses their skill/command partition | A separate agent/service for every professional discipline adds coordination without proving better advertising |
| Reuse | Derive inspected methods and invoke eligible existing tools through exact contracts | Copy an entire marketing runtime or treat every candidate as an implementation ticket; this imports unneeded ownership and hidden assumptions |
| Evidence | Link exact approved facts, generated expressions, observations and decisions with their scope | Create a universal knowledge store whose copies silently replace business, legal or analytics truth |
| Production | Choose the cheapest representation that can answer the current question and require actual outputs at the requested fidelity | Generate every possible angle/format first or call a direction file a finished asset |
| Automation | Automate deterministic repetitive checks only when their exact contract and failure behaviour justify it | Build a general orchestrator, ad server, attribution engine or quality predictor before actual domain proof |
| Extension | Add a pack only for a meaningful reusable campaign grammar with independent evidence | Platform-labelled packs, duplicated core logic or untested advice presented as specialisation |
| Evaluation | Separate exact validation, qualitative judgement, external authority and empirical evidence | Rank everything by one score or call a small synthetic review a campaign benchmark |
| State and integration | Reuse scoped lineage/learning records; optional Pactwright owns its own lifecycle | Require a manual graph or local lifecycle clone so the otherwise standalone skills can run |

These choices are complete Stage 13 decisions. They do not finalise Stage 14's four-skill hypothesis, select Stage 15's complete pack catalogue, choose Stage 16's fifteen primary cases, or design Stage 18's executable benchmark architecture. Each later stage must perform its own specified analysis and produce every required output.

## 6. Over-engineering guardrails

Lean means removing unnecessary machinery, not missing mandatory capability, evidence or exact counts. Each guardrail pairs a positive operating rule with a concrete rejection or repair. None can be used to waive the original bootstrap.

| ID | Guardrail | Required rule | Reject or repair |
|---|---|---|---|
| B01 | Domain ownership before convenience | A proposed feature must identify its advertising decision and preserve upstream offer, price, segment, economics and legal authority. | Reject a pricing optimiser or generic customer/CRM system disguised as campaign repair; route the actual business issue upstream. |
| B02 | One task can use one readable record | Logical brief, claim, variant, decision and evidence records may share a file while retaining their identities and exact dependencies. | Reject mandatory files, agents or services per logical field; also reject deleting required fields merely to make the document short. |
| B03 | One authoritative source for meaning | Keep original commercial, claim, approval and metric revisions; summaries and vendor context are derived views, not competing editable truth. | Reject drift by silent copying, default zero values or changed event names. Repair the affected representation and preserve the source. |
| B04 | Host capability is reused | Use the accepted Agent Skills host and existing workspace/tools. Core text work must not need six ad accounts, a new server or a paid design suite. | Reject an owned scheduler, multi-agent control plane, account database or universal model gateway unless a later explicitly authorised requirement genuinely changes scope. |
| B05 | Execution profiles are not campaign grammars | Describe exact provider/product/action constraints in profiles; packs alter reusable advertising grammar and priorities within core contracts. | Reject one pack per platform or one universal API mapping merely because several vendors expose objects called campaign or conversion. |
| B06 | Smallest sufficient actual representation | Choose fidelity by the next uncertainty and requested output. Cheap review can reduce waste, but cannot stand in for required final artwork, video, audio or execution evidence. | Reject both expensive mass generation before selection and a prompt/storyboard submitted as a required finished asset. |
| B07 | Existing scoped authority is preserved | Apply Stage 12 effects, recipient and exposure checks. Already supplied exact authority need not be requested repeatedly; new effects require their own scope. | Reject autonomous scale, silent provider substitution, blind billable retry and permission-reset claims inferred only from discovery. |
| B08 | Helpers need a demonstrated deterministic job | A proposed local helper must identify a repeated check, precise input/output contract, failure cases, ownership and why an existing tool is insufficient. | Candidate checks include identifiers, links, counts, schemas and arithmetic; reject a general workflow framework, opaque quality predictor or a script for every natural-language command. |
| B09 | Validation does not replace domain evaluation | Keep all twelve original evaluation responsibilities independently inspectable. Structural validity does not establish a truthful claim, good creative, valid inference or legal conclusion. | Reject a universal advertising quality score or averaged-away hard failure; a missing source/approval remains blocking even when copy is persuasive. |
| B10 | Lineage without a new graph platform | Retain exact parents, revisions, changed/fixed elements and contextual state. Derive views from those records rather than demand manual graph maintenance. | Reject a universal audience graph, custom lifecycle engine or mandatory Pactwright clone. Optional composition returns domain evidence to Pactwright. |
| B11 | Packs are bounded additions | Keep common evidence, approval, artefact and repair rules in core. A selected pack must demonstrate its specific behavioural difference and own its tests/showcase. | Reject copied core workflows, generic guidance relabelled as a pack, and pack instructions that override verified constraints or approved business decisions. |
| B12 | Examples and exact counts are acceptance obligations | The fifteen primary examples remain exactly three per level with complete prompts and required artefacts/evaluations; mature packs retain all their evidence obligations. | Reject fewer examples, placeholder directories, duplicated cases counted as breadth or an unexecuted differential described as a result. |
| B13 | Runtime claims follow actual evidence | Record designed, generated, received, evaluated, approved, serving and measured as different facts. Synthetic observations stay synthetic in every exported result. | Reject promotion from a research log, successful tool status or structural test to working, benchmarked, mature or legally cleared. |
| B14 | External absence is handled by responsibility | A missing live tool may leave valid file-based reasoning available, but cannot waive an actual required output or unresolved user decision. Preserve the same contract for a permitted alternative. | Reject filling missing account facts, proof, private histories or identity assets with invented evidence. Under this bootstrap, a user-dependent blocker stops stage progression. |

### Admission test for any new helper or dependency

A proposal must identify the original domain requirement and a concrete task/example that needs it; the existing capability considered; the precise gap it closes; the smallest implementation or reuse choice; input/output and ownership boundaries; effects on data, cost and authority; tests that distinguish correct from unsafe behaviour; and the maintenance/removal consequence. A future possibility, repeated vocabulary or a collection of attractive vendor features is insufficient.

For a deterministic helper, prefer a small directly testable function or command over a framework. Identifier/reference validation, exact prompt/example counts, controlled-change comparison and compatible-unit arithmetic are candidate responsibilities because the accepted models contain such constraints. This is permission to justify those helpers later, not a decision that all must be built. Statistical computation, asset rendering, serving and hosting remain external where the original assigns them; a need to inspect their results does not transfer ownership.

For an extension or shared abstraction, require a genuinely distinct behaviour or demonstrated recurring need, preserve core contracts and record the counterexample that would invalidate extraction. Stage 27 owns the final shared-candidate review. Do not invent a rigid generic hierarchy or an extra cross-domain framework from similar field names. Any necessary new user-owned scope or authority decision is raised rather than silently applied.

## 7. Closure order, proof and unresolved-input handling

Prioritise by dependency and irreversible risk, not by provider popularity or how many integrations can be listed. First ensure the instruction contracts can preserve commercial truth, source/approval distinctions and actual-output requirements. Then prove those behaviours through the required vertical and targeted negative cases. Broader formats, packs and examples retain their full assigned coverage and are not demoted to optional nice-to-have work.

|---|---|---|
